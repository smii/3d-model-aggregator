# Internationalisation (i18n)

Dependency-free, cookie-based UI translation. There are no locale-prefixed routes: `/favorites` is `/favorites` in every language.

Status: foundation only. Navigation, the header (language switcher, sign-in) and the user menu are translated. Everything else is still English and is meant to be migrated incrementally (see below).

## File map (`src/lib/i18n/`)

| File | Runs on | Purpose |
| --- | --- | --- |
| `config.ts` | both | `LOCALES` (code + native name), `DEFAULT_LOCALE`, cookie name/lifetime, `isLocale()` |
| `negotiate.ts` | both (pure) | `matchLocale()`, `negotiateLocale()` for `Accept-Language` |
| `messages/en.ts` | both | English **source** catalog; defines `MessageKey` |
| `messages/es.ts` | server | Spanish demo catalog (machine-translated, **not natively reviewed**) |
| `catalogs.ts` | server only | registry + `getMessages(locale)` (locale laid over English) |
| `translate.ts` | both (pure) | `createT()`, `{param}` interpolation |
| `server.ts` | server | `getLocale()`, `getI18n()`, `getT()` |
| `client.tsx` | client | `I18nProvider`, `useT()`, `useLocale()` |
| `actions.ts` | server action | `setLocaleAction()` sets the cookie |

UI: `src/components/LanguageSwitcher.tsx` (header). The root layout (`src/app/layout.tsx`) resolves the locale, sets `<html lang>` and wraps the body in `I18nProvider`.

Never import `catalogs.ts` or `messages/es.ts` from a client component: that would ship every language to the browser. Client components get strings only through `useT()`.

## Locale resolution

1. `NEXT_LOCALE` cookie, if its value is exactly one of the codes in `LOCALES`.
2. `Accept-Language` header (q-values honoured; `es-MX` matches `es`).
3. `en`.

An unknown, malformed or tampered cookie value is ignored as if absent, so detection continues with `Accept-Language` and then English. Nothing is ever rendered from an unvalidated value.

The cookie is set by the `setLocaleAction` Server Action: `Path=/`, `SameSite=Lax`, one year, not `Secure` (would break plain-http LAN use), not `HttpOnly` (it is a preference, not a credential). The action validates its argument against `LOCALES`. Because it sets a cookie, Next re-renders the current route in the same response, so the page switches without a manual reload.

Reading cookies/headers makes the root layout dynamic. The app already was (the header calls `auth()`); with `HIDE_GMAIL_FEATURES=true` pages that could have been static are now dynamic too.

## Using translations

Server component:

```tsx
import { getT } from "@/lib/i18n/server";
const t = await getT();
return <h1>{t("nav.search")}</h1>;
```

Client component:

```tsx
import { useT } from "@/lib/i18n/client";
const t = useT();
```

Parameters: `t("greeting", { name })` with `"greeting": "Hello {name}"`. A placeholder without a param is left as written. There is no plural/ICU/RTL support yet; add it when a string needs it.

Missing keys fall back to English per key (an absent or blank translation counts as missing). A key that is not in English at all renders as the key itself, but `t()` is typed on `MessageKey`, so that cannot compile.

Nav items (`src/lib/nav-items.ts`) carry an optional `labelKey`; `label` is the English fallback. New nav items should set both.

## Incremental string extraction

Do not sweep the codebase. When you touch a component for another reason, or a feature is worth localising:

1. Add keys to `messages/en.ts`, grouped by prefix (`nav.`, `auth.`, `favorites.`, ...). Keys are flat, dot-separated, camelCase after the prefix.
2. Replace the literal with `t("key")` (`getT()` on the server, `useT()` in `"use client"` files).
3. Optionally add translations to the other catalogs. Skipping is fine, English shows.
4. Keep brand names ("3D Model Aggregator", platform names) untranslated.

All strings of the active locale are sent to the browser with the page. That is negligible now; if the catalog grows large, split it by prefix and pass only the needed namespaces to the provider.

## Adding a locale

1. Add `{ code: "de", name: "Deutsch" }` to `LOCALES` in `config.ts` (name in the language itself).
2. Create `messages/de.ts` exporting a `Catalog` (any subset of the English keys).
3. Register it in `CATALOGS` in `catalogs.ts` (a missing entry is a compile error).

The switcher, `Accept-Language` matching and `<html lang>` pick it up automatically. Check that long translations fit the 11px mobile bottom bar and the 360px header.

## Spanish demo catalog

`messages/es.ts` is machine-translated and not reviewed by a native speaker; its header says so. Have a native speaker review it before treating it as production copy, then remove the warning.

## PWA / service worker behaviour

`public/sw.js` is not changed by i18n. It ignores non-GET requests, so the language-switch Server Action always goes to the network. Document navigations are network-first with a cache fallback.

- **Online:** a language switch is visible immediately, and every later navigation fetches a fresh page that carries the cookie's language. Verified in a browser with the worker active.
- **Offline:** the app shell is served from the cache in whichever language that page was last fetched. Switching language offline does nothing (the action cannot reach the server; the switcher keeps the current language and the page stays usable).
- Pages cached before a switch stay in the old language until visited again online.
- `/settings`, `/sync`, `/favorites/likes` and `/api/*` stay bypassed by the worker, as before. The shell (nav, header) on those pages is translated like everywhere else; their own content is untouched.
- `CACHE_NAME` did not need a bump: the cache is keyed by URL and always refreshed from the network first.

## Known limitations

- Only nav, header and user-menu strings are translated.
- No locale-specific number/date formatting, plurals or RTL.
- `<title>`/metadata are still English.
- Search results and third-party content are never translated.
